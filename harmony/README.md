# harmony — the HarmonyOS client

Generated by `react-native init-harmony` and consumed by DevEco Studio. The JS
comes from the same `src/` as iOS and Android; what lives here is the native
shell.

## Building without DevEco Studio

DevEco bundles its own toolchain, so no separate install is needed:

```sh
export DEVECO=/Applications/DevEco-Studio.app/Contents
export PATH="$DEVECO/tools/node/bin:$DEVECO/tools/ohpm/bin:$DEVECO/tools/hvigor/bin:$PATH"
export DEVECO_SDK_HOME="$DEVECO/sdk"

cd harmony && ohpm install          # resolves the RNOH .har
cd .. && npx react-native bundle-harmony --dev false
cd harmony && hvigorw assembleHap
```

Output: `entry/build/default/outputs/default/entry-default-unsigned.hap`.

Unsigned, as the name says — hvigor warns `Will skip sign 'hos_hap'. No
signingConfigs profile is configured`. Signing needs a Huawei developer account
and is done through DevEco (File > Project Structure > Signing Configs >
Automatically generate signature). Until then the HAP cannot be installed on a
device.

## Running it

`build-profile.json5`, `hvigorw` and `hvigor/hvigor-wrapper.js` are all
gitignored by the scaffold — DevEco regenerates them. A fresh clone therefore
needs the project opened in DevEco once before the commands above work.

Then: start Metro (`npm start`), open this directory in DevEco, and debug the
`entry` configuration. `Index.ets` prefers `MetroJSBundleProvider` in debug and
falls back to the bundled `hermes_bundle.hbc`.

## What is wired up

`Index.ets` mounts `RNApp` with `appKey: "Chatterbox"`, matching
`AppRegistry.registerComponent` in the repo root `index.js` via `app.json`.
Bundle id is `com.chatterbox.app`, the same as Android.

Firebase works here through the JS SDK rather than React Native Firebase — see
`src/services/firebase/README.md`, particularly its "Known gaps" section. Push
notifications, App Check, Analytics and Crashlytics are all absent on this
platform, and the reasons are per-service rather than incidental.

## Third-party native modules

20 of ~26 native dependencies are linked and compiling: async-storage,
clipboard, flash-list, geolocation, netinfo, audio-recorder-player, blob-util,
document-picker, gesture-handler, get-random-values, haptic-feedback,
image-picker, image-resizer, image-viewing, incall-manager, linear-gradient,
localize, safe-area-context, screens, svg, video. Each is
`@react-native-oh-tpl/<name>` installed at the JS level, redirected
automatically by Metro (RNOH scans `node_modules` for a `harmony.alias` field
in each port's `package.json` — see `createHarmonyMetroConfig` in
`@react-native-oh/react-native-harmony`, no custom resolver needed).

Whether a port needs anything beyond that npm install depends on whether it
ships a `harmony/*.har`. Most don't — they're pure ArkTS/TS over primitives
RNOH's core already provides, so installing is the whole job, and hvigor
never needs to know they exist. `scripts/link-harmony-natives.py` reports
which ones do (read-only — it used to also write dependency entries, until
testing showed hvigor's own autolink already handles that; see the script's
own docstring for how that was confirmed).

### The two-pass build, and why it exists

For a port that *does* ship native code, hvigor's autolink discovers it from
`node_modules` and writes the dependency into `harmony/oh-package.json5` —
but it does this **as part of the same `assembleHap` run** that then tries to
compile against what it just declared, before `ohpm install` has fetched it.
A freshly-installed native port's first build always fails on a
missing-module error that has nothing to do with the port itself.

`scripts/build-harmony.sh` handles this: it lets the first `assembleHap` fail
on purpose, runs `ohpm install` again to fetch what autolink just declared,
applies `scripts/patch-harmony-natives.sh`, then assembles a second time.
Run it whenever a new `.har`-shipping port is added; for everything already
committed (including gesture-handler and screens below) it's still needed,
because ohpm's extracted copy — where the patches live — gets wiped and
re-extracted from scratch on every `ohpm clean` / fresh checkout.

### gesture-handler and screens: fixed, four patches deep

Both ports were built against an older RNOH/RN pairing than the 0.84.2 core
this app is on. Found and fixed by actually compiling, not by inspection —
each error pointed at the next one:

1. **ArkTS interface gap.** The port's package class extended the deprecated
   `RNPackage` base; current RNOH core requires `RNOHPackage`, a strict
   superset (`RNOHPackage extends RNPackage`, adding one method with a safe
   default). Swapping the import and `extends` clause is behavior-preserving.
2. **C++ class name mismatch.** hvigor's autolink generates
   `RNOHPackagesFactory.h` expecting a class named e.g.
   `ReactNativeOhTplReactNativeGestureHandlerPackage` (derived from the npm
   package name), but the port's C++ produces
   `RnohReactNativeHarmonyGestureHandlerPackage` — a name from before this
   naming convention existed. Fixed with a one-file alias header, the same
   pattern the port's own author already used once for an even older
   deprecated name (`GestureHandlerPackage.h` / `ScreensPackage.h`, still
   present, aliasing to the `Rnoh*` name).
3. **Moved React Native header.** gesture-handler's C++ does
   `#include <react/renderer/debug/SystraceSection.h>`. RNOH's vendored RN
   source tree now keeps that file at
   `third-party/rn/ReactCommon/cxxreact/SystraceSection.h` — a real Meta-side
   reorganization the port predates. Fixed with a redirect header at the old
   path, `#include`ing the real one by relative path.

All four are in `scripts/patch-harmony-natives.sh`, applied to ohpm's
*extracted* copy under `harmony/oh_modules/` (the `.har` itself is a zip
patch-package can't diff), and re-created idempotently on every run since
that extraction gets wiped on a clean install. Verified: both `.so` files
(`librnoh_gesture_handler.so`, `librnoh_screens.so`) are present inside the
built HAP, and a from-scratch rebuild (`rm -rf harmony/oh_modules` and
friends, then `scripts/build-harmony.sh` alone) reproduces a working HAP with
zero manual steps.

There's a fifth fix at a different layer: the oh-tpl `screens` port (based on
upstream v3.34) does a deep import of
`react-native-screens/src/native-stack/contexts/GHContext`, a path our real
`react-native-screens` (v4.23) no longer has — `GHContext` moved to
`../../contexts` during a refactor upstream predates. This one's a plain JS
module living in `node_modules/`, not ohpm's extracted copy, so it's tracked
the normal way: `patches/react-native-screens+4.23.0.patch` (applied
automatically by the existing root `postinstall`), restoring the old path as
a one-line re-export rather than touching the oh-tpl port itself.

### mmkv: reimplemented, not ported

`react-native-mmkv` v4 depends on Nitro Modules, which has no RNOH port
anywhere — not even an unofficial one. The only harmony port that exists
(react-native-oh-library/react-native-mmkv on GitHub) targets the pre-Nitro
v3 API and is unpublished to any registry, meaning using it would mean
running a different major version of the library on one platform only.

`src/services/storageMMKV.ts` turned out to be the sole importer of
`react-native-mmkv` in the whole app, and its exported interface was already
fully async — so `storageMMKV.harmony.ts` reimplements the same interface on
`@react-native-async-storage/async-storage` (which does have a port) instead
of porting MMKV itself. Two properties of the original had to be preserved
deliberately:

- **Encryption at rest.** MMKV encrypts its file with a per-device key; that
  store holds the E2EE secret key, so losing that protection here would be a
  real regression. Every value is encrypted with the app's own
  XChaCha20-Poly1305 primitives (`services/crypto.ts`, the same cipher
  `e2ee.ts` uses for messages) before reaching AsyncStorage.
- **Synchronous reads.** `getBoolean`/`setBoolean`/`getNumber`/`setNumber`/
  `remove` are synchronous in the original — MMKV is memory-mapped, so there
  is no bridge crossing to wait on. AsyncStorage's bridge call is
  unavoidably async, so these are backed by an in-memory cache populated
  once at module load; writes land in the cache immediately and persist to
  AsyncStorage in the background.

The one gap that can't be closed: between module load and that first
population finishing, a synchronous read returns "not set" for a key that
does have a saved value. Every call site already treats "not set" as "use
the default" (`?? false`, `?? 0`), so the practical effect is a brief
cold-start window where privacy/security toggles could read as their
default. `appLock.ts`'s `isAppLockEnabled`/`isBiometricsEnabled` are the two
places that window actually matters — check those first when this runs on a
real device.

Verified: the harmony bundle contains zero references to `react-native-mmkv`
or `NitroModules`; iOS's bundle still contains real MMKV, unaffected.

### vector-icons: turned out to be a non-issue

`react-native-vector-icons` is declared in `package.json` but has zero real
imports anywhere in `src/` — every match for it is a comment. The app built
its own SVG-based `Icon.tsx` specifically to avoid the native font linking
that library needs (see that file's own header). Nothing to port; the
dependency is dead weight worth removing separately, unrelated to this port.

### biometrics: degrades cleanly, doesn't crash

`react-native-biometrics` has no HarmonyOS port anywhere, and unlike
Firebase there's no pure-JS fallback to reach for — biometric auth is a
native OS capability, not a network API. `appLock.ts` was its sole importer;
that's now `src/services/biometrics.ts` / `.harmony.ts`, and the harmony side
simply reports "unavailable."

That's not a workaround — it's what `appLock.ts`'s own existing try/catch
already produced on a real device with no sensor, so `isBiometricsAvailable()`
returning `false` already hides the biometric-unlock option from the UI with
no new handling needed anywhere. A real implementation would mean writing a
new RNOH TurboModule against HarmonyOS's own `@ohos.userIAM.userAuth`, which
is new native authoring rather than porting or gluing an existing port —
out of scope here.

`webrtc` is out of scope for v1 per the original port plan (calling was
always going to be the largest single item).

It used not to behave that way. `IncomingCallManager` is mounted in `App.tsx`
for every signed-in user, and it imported `RTCView` and `mediaDevices` straight
from `react-native-webrtc` — a package with no `@react-native-oh-tpl` twin.
That package throws from module scope:

```js
const {WebRTCModule} = NativeModules;
if (WebRTCModule === null) { throw new Error('WebRTC native module not found.') }
setupNativeEvents();
```

and the check is `=== null` while an unregistered native module is `undefined`,
so it misses and `setupNativeEvents()` builds a NativeEventEmitter over
nothing. Either way the failure lands at import, on the startup path. "Calling
is out of scope" was implemented as "the app does not start".

There is a `services/webrtc.ts` / `webrtc.harmony.ts` pair now, like the
Firebase ones, and the two call sites import from it. The HarmonyOS half
renders nothing for `RTCView`, rejects `getUserMedia`, and throws from every
constructor with a message naming the file — a peer connection that silently
never connects is the quiet-failure shape this codebase keeps finding.

Verified as far as it can be without a device: bundling for `harmony` drops
`WebRTCModule` from 14 references to none, while the Android bundle keeps all
14. The gap is now a gap rather than a crash; calling itself is still out of
scope.
